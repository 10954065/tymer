# Database Design

PostgreSQL (Neon in production, PostgreSQL 17 locally). Schema source: `src/server/db/schema/*`.
Migrations: `drizzle/*.sql` (generated by drizzle-kit plus hand-written integrity migrations).

## Conventions

- **Money** is stored as `bigint` **pesewas** (1 GHS = 100 pesewas). No `numeric`/`float` money columns.
- **Timestamps** are `timestamptz` (UTC). Business days are computed in `Africa/Accra`.
- **Business dates** (expense date, purchase date, cash session date) are `date` columns.
- **IDs**: `uuid` (`gen_random_uuid()`) for entities, `bigserial` for high-volume ledgers
  (`inventory_movements`, `audit_logs`, `product_price_changes`).
- **Document numbers** (`SAL-000123`, `PAY-…`, `ORD-…`, `PUR-…`, `SPY-…`, `EXP-…`, `RET-…`) come from
  PostgreSQL sequences, so they are unique and gap-tolerant under concurrency.

## Tables

### Identity & configuration
| Table | Purpose |
| --- | --- |
| `users` | Staff accounts. Role: `OWNER`, `MANAGER`, `CASHIER`, `INVENTORY_STAFF`. Lockout counters. Username unique case-insensitively. |
| `sessions` | Server-side sessions. PK is SHA-256 of the cookie token (the raw token is never stored). Expired rows are purged by the cleanup job. |
| `business_settings` | Single row (`id = 1`): business details, receipt footer, negative-stock policy, cashier discount limit, tax rate. |

### Catalogue & inventory
| Table | Purpose |
| --- | --- |
| `categories` | Product categories (name unique case-insensitively). |
| `suppliers` | Supplier contacts. |
| `products` | Current product state: prices (weighted-average `cost_price`, `selling_price`), `quantity`, status (`ACTIVE`, `OUT_OF_STOCK`, `ARCHIVED`, `DISCONTINUED`), `out_of_stock_at`, `archived_at`. SKU unique (upper-case), barcode unique when present. |
| `product_price_changes` | Append-only history of cost/selling price changes. |
| `inventory_movements` | **Append-only stock ledger.** One row per change to `products.quantity` with previous/new quantity, unit cost, reference and user. CHECK: `new = previous + change`, `change <> 0`. |

### Sales
| Table | Purpose |
| --- | --- |
| `customers` | Customer profiles (phone unique when present). Walk-in sales have no customer. |
| `sales` | Sale header with immutable totals (`subtotal`, `discount_total`, `tax_total`, `total`, `cost_total`), unique `idempotency_key`, `source` (`POS`/`OFFLINE`), void fields. CHECK: `total = subtotal - discount + tax`. |
| `sale_items` | Line snapshots: product name, SKU, unit cost, unit price, discount, tax, line total. Only `returned_quantity` may change (and only upwards). |
| `sale_returns`, `sale_return_items` | Customer returns (append-only): value reversed, tax reversed, restocked cost. |
| `sync_devices` | Devices that synchronise offline sales. |

### Orders (custom decoration jobs)
| Table | Purpose |
| --- | --- |
| `orders` | Order header: customer, agreed `total_amount`, estimated material/labour costs, `product_cost_total` (snapshot at completion), status lifecycle, completion/cancellation timestamps. Completed/cancelled orders are final. |
| `order_items` | Products (linked to stock) and services with quantity, unit price and line total. |

### Money ledgers
| Table | Purpose |
| --- | --- |
| `payments` | **Append-only customer payment ledger.** Signed amounts: `RECEIPT > 0`, `REFUND < 0`, `REVERSAL < 0` (references the reversed receipt, at most once). Exactly one of `sale_id` / `order_id`. |
| `purchases`, `purchase_items` | Stock purchases from suppliers. `DRAFT → RECEIVED` (stock in) or `CANCELLED`. Received purchases are final; items editable only while draft. |
| `supplier_payments` | Append-only payments to suppliers (`PAYMENT > 0`, `REVERSAL < 0`). |
| `expense_categories`, `expenses` | Operating expenses. Amount/date/method immutable; corrections use a reversal row (negative, same date) + a new expense. Expenses linked to an order are direct order costs. |
| `cash_sessions` | Daily cash drawer: opening balance, snapshot of cash in/out at close, expected vs actual, difference and explanation. Closed sessions are final. |

### System
| Table | Purpose |
| --- | --- |
| `audit_logs` | Append-only audit trail (user, action, entity, changed fields before/after, reason, reference). |
| `sync_conflicts` | Offline sales that failed validation (stock/price). Never deleted; resolved by the owner (record or dismiss). |
| `backup_runs` | Results reported by the backup workflow (size, checksum, verification). |

## Relationships (summary)

```
categories 1─* products *─1 suppliers
products 1─* inventory_movements, product_price_changes, sale_items, purchase_items, order_items
customers 1─* sales, orders, payments
sales 1─* sale_items, sale_returns, payments
sale_returns 1─* sale_return_items *─1 sale_items
orders 1─* order_items, payments, expenses(direct costs)
suppliers 1─* purchases 1─* purchase_items, supplier_payments
users 1─* (created_by / received_by / user_id on every ledger)
```

## Financial integrity rules (enforced in the database)

1. `inventory_movements`, `payments`, `supplier_payments`, `audit_logs`, `product_price_changes`,
   `sale_returns`, `sale_return_items` reject every `UPDATE` and `DELETE` (trigger `slb_forbid_change`).
2. `products`, `sales`, `sale_items`, `orders`, `expenses`, `customers`, `cash_sessions`,
   `sync_conflicts`, `purchases` reject `DELETE` (archive / void / cancel instead).
3. Sale totals, sale item snapshots and expense amount/date/method cannot be modified.
4. A voided sale cannot be reinstated; completed/cancelled orders and closed cash sessions are final.
5. CHECK constraints guarantee arithmetic consistency (sale totals, line totals, movement balances,
   payment signs, non-negative prices and quantities).
6. Stock decrements use a conditional `UPDATE … WHERE quantity >= n` inside a transaction, so two
   devices can never oversell the same unit (unless negative stock is explicitly enabled in settings).

## Indexes

Indexes were chosen for the actual access paths and kept minimal to save storage and write cost:

- Lookups: `products(upper(sku))` unique, `products(barcode)` partial unique, `users(lower(username))`.
- Listing/filtering: `products(status, name)`, `orders(status, created_at)`, `customers(lower(full_name))`.
- Reporting by time: `sales(created_at)`, `payments(received_at)`, `expenses(expense_date)`,
  `sale_returns(created_at)`, `orders(completed_at)`, `inventory_movements(created_at)`.
- Foreign-key joins: `sale_items(sale_id)`, `sale_items(product_id)`, `payments(sale_id|order_id|customer_id)`, etc.
- Ledger history per product: `inventory_movements(product_id, id)`.

## Financial definitions used by reports

| Metric | Definition |
| --- | --- |
| Gross sales | Σ `sales.subtotal - discount_total` of non-voided sales in the period (tax excluded). |
| Returns | Σ `sale_returns.value_total` recorded in the period. |
| Order revenue | Σ `orders.total_amount` of orders **completed** in the period. Deposits are not revenue. |
| Net revenue | Gross sales − returns + order revenue. |
| Cash collected | Σ `payments.amount` received in the period (receipts minus refunds/reversals). |
| COGS | Σ `sales.cost_total` (historical unit costs) − Σ restocked cost of returns + order product costs + direct order costs (expenses linked to orders completed in the period). |
| Gross profit | Net revenue − COGS. |
| Operating expenses | Σ `expenses.amount` in the period not linked to an order (reversals included, so corrections net out), plus direct costs of orders cancelled in the period. |
| Net operating profit | Gross profit − operating expenses. |
| Receivables | Sales: `total − returned value (incl. tax) − net payments`; completed orders: `total_amount − net payments`. |
| Inventory valuation | Σ `products.quantity × products.cost_price` (weighted-average cost) for quantity > 0. |

Stock purchases are **not** expenses: they increase inventory value (and reduce cash through supplier payments);
their cost reaches the P&L only as COGS when goods are sold.
